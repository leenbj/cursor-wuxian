# 同窗口多对话隔离（分组隔离）规格与计划

日期：2026-10-19　状态：已实现并验证（需重载 MCP 服务器后在本机生效）

## 1. 问题

一个 Cursor 窗口只拉起一个 MCP 进程 → 一个 `WebUIManager` → 一个 `current_session`。
同一窗口里并行的多个对话共用它：

1. 对话 B 调用 `create_session`，会清理并顶替对话 A 的会话，窗口与 WebSocket 被抢走。
2. 对话 A 下一次轮询发现自己的会话已是终态，又新建会话顶替 B。
3. 结果：窗口内容互相覆盖，用户的回复可能回给错的对话。

不同 Cursor 窗口本来就是不同进程、不同端口，天然隔离，不在本次范围。

## 2. 目标与非目标

目标

- G1 同一进程内不同对话各自独立：独立端口、独立窗口（标题 = 任务名）、独立会话，互不顶替、互不清理。
- G2 只有一个对话时，行为与改造前完全一致（默认端口、窗口复用、误关重开、结束按钮）。
- G3 对话结束后释放分组，管理器可被后续对话复用，端口数不随对话总数增长。
- G4 「提交反馈后关窗」「结束对话后关窗」只关自己对话的窗口。

非目标

- 不改 Tauri / Rust 与发布二进制（改动会触发 CI 重建并产生机器人提交）。
- 不做「一个窗口多标签页」。
- 不区分「同目录且同标题」的两个对话（视为同一对话，见 §5）。

## 3. 设计：每个分组一个独立管理器

管理器内部（端口、窗口、单会话逻辑）不动，只在 `web/main.py` 加一层注册表。

- **分组键**：`(realpath(project_directory), title.strip())`。
- **路由优先级**：携带的 `session_id` 若属于某个管理器 → 用该管理器（并把本次的键也登记为别名，标题漂移自愈）；否则按分组键；都没有 → 认领一个管理器。
- **认领顺序**：先复用空闲管理器（默认管理器优先，所以单对话时仍是 8765、行为不变）；没有空闲的才新建。
- **新建管理器的端口**：显式传入「比已有管理器端口更大且探测为空闲」的端口，且 `auto_cleanup=False`。
  不能走 `WebUIManager()` 的默认路径：该路径在非测试模式下 `auto_cleanup=True`，端口被占用且占用者命令行含 `mcp-feedback-enhanced` 时会尝试杀掉占用进程。同一进程内第二个管理器看到的占用者就是自己（macOS 上 `psutil.net_connections` 无权限而返回空所以不触发，Linux 上会触发）。
- **释放**：`interactive_feedback` 返回 `[CONVERSATION_ENDED]` 时，注销该管理器的所有键；管理器本身保留，供下一个新对话复用（`stop()` 不会真正停掉 uvicorn 线程，所以不销毁）。
- **桌面窗口插线**：`DesktopApp` 增加可选的 `web_manager` / `window_title` 参数，窗口连到自己分组的服务；不传则沿用全局默认管理器。`src/…/desktop_app.py` 与 `src-tauri/python/…/desktop_app.py` 两份字节一致（已有测试守护）。
- **关窗隔离**：`WebFeedbackSession` 增加 `on_close_window` 回调，由所属管理器在 `create_session` 时注入；提交反馈后关窗改用它，不再取全局默认管理器。
- **`stop_web_ui()`**：停止默认管理器与所有额外管理器，并清空注册表。

## 4. 备选方案

| 方案 | 结论 |
| --- | --- |
| 单管理器内按会话路由（`/ws?session=`、`/api/*` 全改） | 前端、路由、窗口重开全按「当前会话」建模，改动面大、回归风险高，未选 |
| 每分组一个管理器（本方案） | 管理器内部零改动，隔离由端口天然保证，选用 |
| 一个窗口多标签页 | 与「一个对话一个窗口、标题随任务」冲突，未选 |

## 5. 已知限制（需要写进使用规则）

- 并行对话必须用不同的 `project_directory` 或不同的 `title`；同目录同标题会共用一个窗口。
- 同一对话内 `title` 必须保持完全一致，否则会被当成新分组、多开一个窗口（若调用携带 `session_id` 则不受影响）。
- 同时存在的对话越多，占用的本地端口和窗口越多；对话结束（红按钮）后管理器才可复用。
- 修改生效需要重载 MCP 服务器（Cursor 设置 → MCP → 关/开），正在运行的旧进程仍是旧行为。

## 6. 验收标准（均由测试证明）

1. 两个不同分组各得到不同的管理器；B 建会话后 A 的会话仍存活、仍是 A 的 `current_session`；A 再次轮询不会新建会话。
2. 带 `session_id` 的续接路由到会话所属的管理器，即使标题/目录参数不同或为空。
3. 只有一个对话时用默认管理器；第二个并发分组得到新管理器且端口互不相同、不触发 `auto_cleanup`。
4. 对话 `ended` 后分组被释放，下一个新对话复用该管理器，不再新建。
5. 提交反馈后只关本分组的桌面窗口，另一个分组的窗口不受影响。
6. `DesktopApp` 注入管理器后连接的是该管理器的地址；两份 `desktop_app.py` 仍字节一致。
7. 既有单元测试无新增失败（基线：224 通过、2 个历史失败）。

## 7. 追加修复：点「结束对话」落在两次轮询之间时信号会丢（端到端验证时发现）

v2.9.0 即存在的缺陷，非本次改动引入。每个 45 秒时间片之后，模型要经过一轮往返才会发起下一次续调；用户恰好在这段空档点结束时，会话已是终态，`launch_web_feedback_ui` 把它当「旧会话」丢弃并新建会话：用户点了结束却看到新窗口，模型拿到的是 `waiting` 而不是 `ended`。

修复：会话增加 `end_delivered` / `is_end_pending()`。结束信号未交付前，续调不丢弃该会话、`session_id` 路由也继续认它（标题漂移时同样不丢信号）；交付一次（返回 `ended`）后才算收尾，之后同 id 的调用视为新一轮，不会永远被 `ended` 挡住。

## 9. 验证结果

- `tests/unit/test_group_isolation.py`：15 个用例；17 个人为变异（逐项破坏实现）全部被对应用例抓到。
- 全量单元测试：239 通过、2 个失败；这 2 个（`test_status_update_resets_timer`、`test_session_feedback_submission`）在基线提交 `e43b922` 上同样失败，与本次改动无关。
- 真实端到端（同进程两个真实服务 + 真实 WebSocket + 并发续调）：17/17 通过——两个对话分别在相邻端口；回复只到目标对话；结束一个不影响另一个；结束后新对话复用被释放的管理器、额外管理器数不增长。
- 未覆盖：真实桌面壳（Tauri）下的多窗口实机表现。桌面壳读 `MCP_WEB_URL` / `MCP_WINDOW_TITLE`、不做单实例限制，代码路径已由注入测试覆盖，但没有在带图形界面的多窗口场景里实测。
